## Design documentation — functional gaps

- [x] Notification/alerting delivery mechanism was never designed despite three decisions assuming it exists (D-19 Risk Exception reminders, D-24 break-glass alerts, D-26 rejected SAML alerts) — see new `Design_Notification_Framework.md`. **Correction 2026-09-09**: this checkbox is misleading as written — what actually got *built* (D-115/D-116/D-118) uses a different schema and different class names than `Design_Notification_Framework.md` proposed (`web.notification_config`/`notification_recipient`/`dim_notification_type`/`notification_log` and `NotificationRepository`/`SmtpNotificationSender`/`INotificationCheck`, not that doc's `dim_notification_event_type`/`notification_channel` and `NotificationDispatcher`/`INotificationChannel`/`SmtpNotificationChannel`). `Design_Notifications.md` is the doc that matches reality; `Design_Notification_Framework.md` was superseded but carries no note saying so — new item below.
- [x] `Design_Notification_Framework.md` was superseded by what actually shipped under D-115/D-116/D-118 (documented in `Design_Notifications.md`) but isn't marked superseded, retired, or reconciled — a reader following it would look for `NotificationDispatcher`/`INotificationChannel`/`SmtpNotificationChannel`, none of which exist. (2026-09-09) Fixed — added a superseded notice pointing to `Design_Notifications.md`, with a matching cross-reference added there too. Left in place (not deleted) for historical context on the original D-19/D-24/D-26 problem framing.
- [x] No segregation-of-duties control on exception approval (the person who made a change can also approve the exception excusing it) — design not started. **Resolved 2026-09-16**: an admin-configurable, off-by-default toggle (`web.app_config.EnforceRiskExceptionSegregationOfDuties`) blocks the same person from both approving a Risk Exception and linking it to an account, plus a detective report (Reports > Risk Exception SoD) surfacing every historical same-person case regardless of whether enforcement is on. See `Database/37_BlueTrack_RiskExceptionSegregationOfDuties.sql` (numbered 37, not 31 -- renumbered 2026-09-21 when merging past AD Account Discovery's own D-137/D-138, which had already claimed 31-36 on `main`).
- [x] `Design_Risk_Scoring.md`'s own open items (scoring algorithm, 3 of 4 ETL feed shapes) — resolved as of 2026-09-09: D-119 built both scoring candidates behind a dispatcher, and unified the ETL feeds with the admin bulk-CSV-upload mechanic rather than needing real external file formats. See that document's own Implementation Status section.
- [x] Audit log retention (`RetentionDays`, Global Application Configuration) had no enforcement anywhere — found 2026-09-21 while documenting day-2 operations. `web.audit_purge_log` (D-62) existed as a table, but `usp_PurgeAuditLog` was only ever mentioned in a schema comment, never actually written, and nothing scheduled it. **Resolved the same day**: `Database/39_BlueTrack_AuditLogPurgeProcedure.sql` builds the procedure exactly to D-62's original design (deletes `audit_field_change` before its parent `audit_event` rows older than `RetentionDays`, records the run in `audit_purge_log`, no-ops with a logged `'Skipped'` status if `RetentionDays` is still unset); `Database/40_BlueTrack_ScheduleAuditLogPurgeJob.sql` schedules it nightly at 3:00 AM (one hour after Import+Load), following the same "never through `App/Migrator`, msdb-only" convention as `14`/`38`. Two new Integration tests cover both the real-purge and the no-op-when-unset paths. Verified live against `BlueTrackTest`: applied `39` via Migrator, ran `40` via `sqlcmd` (confirmed idempotent on a second run), and confirmed the job/schedule/command via `msdb.dbo.sysjobs`. **Not yet applied to the real `BlueTrack` database or scheduled there** — building/testing this was in scope for this pass, turning it on in production is a separate decision.

## Deployment methodology

- [x] No deployment doc existed at all — see new `Design_Deployment_Methodology.md`.
- [x] DPAPI's machine-binding disaster-recovery risk (D-65) — accepted as a known risk; hardened by making the protection scope configurable to the specific account running the application pool rather than machine-wide. See D-106 and `Design_Secrets_Storage.md`.
- [x] `msdb` backup-status permission had no assigned owner (D-97) — designed as a proper SQL Server role (assignable to the app pool account or a separate admin account) rather than a one-off ad-hoc grant. See D-107.
- [x] IIS hosting mechanics were never decided (reverse proxy vs. static hosting) — resolved: static hosting for the built SPA, API behind IIS via ANCM. See D-108 and `Design_Deployment_Methodology.md`.
- [x] No rollback mechanism exists anywhere (Migrator or numbered scripts) — flagged in `Design_Deployment_Methodology.md`'s Open Questions. **Resolved 2026-09-16**: full-database backup/restore (`Deploy/Backup-BlueTrack.ps1`/`Restore-BlueTrack.ps1`, `Deploy/Modules/BlueTrack.Rollback.psm1`), wired into `Install-BlueTrack.ps1` as an automatic pre-deployment backup. Per-script down-migrations remain out of scope by design, not an oversight — see that doc's Open Questions for the exact wording.
- [x] No environment-specific `appsettings.*.json` pattern exists beyond Development — flagged. **Resolved 2026-09-11** (this checkbox was simply never updated at the time): `Deploy/Install-BlueTrack.ps1` writes `appsettings.{Environment}.json` next to the published API output.
