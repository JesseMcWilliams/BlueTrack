## Deployment methodology

- [x] No deployment doc existed at all — see new `Design_Deployment_Methodology.md`.
- [x] DPAPI's machine-binding disaster-recovery risk (D-65) — accepted as a known risk; hardened by making the protection scope configurable to the specific account running the application pool rather than machine-wide. See D-106 and `Design_Secrets_Storage.md`.
- [x] `msdb` backup-status permission had no assigned owner (D-97) — designed as a proper SQL Server role (assignable to the app pool account or a separate admin account) rather than a one-off ad-hoc grant. See D-107.
- [x] IIS hosting mechanics were never decided (reverse proxy vs. static hosting) — resolved: static hosting for the built SPA, API behind IIS via ANCM. See D-108 and `Design_Deployment_Methodology.md`.
- [x] No rollback mechanism exists anywhere (Migrator or numbered scripts) — flagged in `Design_Deployment_Methodology.md`'s Open Questions. **Resolved 2026-09-16**: full-database backup/restore (`Deploy/Backup-BlueTrack.ps1`/`Restore-BlueTrack.ps1`, `Deploy/Modules/BlueTrack.Rollback.psm1`), wired into `Install-BlueTrack.ps1` as an automatic pre-deployment backup. Per-script down-migrations remain out of scope by design, not an oversight — see that doc's Open Questions for the exact wording.
- [x] No environment-specific `appsettings.*.json` pattern exists beyond Development — flagged. **Resolved 2026-09-11** (this checkbox was simply never updated at the time): `Deploy/Install-BlueTrack.ps1` writes `appsettings.{Environment}.json` next to the published API output.
