# Web Interface Design Document — Design Decision Register

**Blueprint Progress Tracking Web Interface**

## Purpose

A single running record of what's been decided about the web interface design, and what's still outstanding, so decisions made in one conversation don't get lost or quietly re-litigated later. Each of the companion design documents (Authentication, Authorization, Secrets Storage, Risk Exception Tracking, Interface Extensibility, Audit Logging, Application Structure, Data & Editing Behavior, Testing Strategy, Accessibility & Theming, Admin Deployment Management, Risk Scoring and its Import companion, Deployment Methodology, Deployment Runbook, Notifications and the superseded Notification Framework, Credentials Management, Dependencies & External Integrations, plus the User Guide/Operations Guide pair) has been updated to reflect the resolved decisions below — this register is the index of all of it in one place, plus everything that hasn't been designed yet at all. **Corrected 2026-09-21**: this paragraph had regrown into two near-duplicate copies (found during a documentation-completeness pass), neither one actually current — collapsed back to one, refreshed against the real file list in this folder.

Update this document as decisions get made, rather than letting resolutions live only in conversation history.

## Resolved Decisions

| ID | Area | Decision | Resolution |
|---|---|---|---|
| D-01 | Authentication | Should a break-glass path exist if all configured providers fail? | Approved — a break-glass path will be included. |
| D-02 | Authentication | Should the login screen remember the last-used provider? | Approved — the login screen will default to the user's last-used provider. |
| D-03 | Authorization | Can a user hold more than one role at once? | Yes — effective permissions are the union of every role a user's group memberships grant. |
| D-04 | Authorization | Do role/permission changes apply immediately, at next login, or something else? | Neither extreme — a "Reload Rights" action (self-service and admin-triggered) refreshes a session's permissions on demand. |
| D-05 | Authorization | Role model structure | Shifted from a fixed role hierarchy to a permission-based model: `app_permission` + `role_permission` (many-to-many), so a permission like `ApproveExceptions` can be granted through more than one role. |
