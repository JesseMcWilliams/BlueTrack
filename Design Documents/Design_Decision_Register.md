# Web Interface Design Document — Design Decision Register

**Blueprint Progress Tracking Web Interface**

## Purpose

A single running record of what's been decided about the web interface design, and what's still outstanding, so decisions made in one conversation don't get lost or quietly re-litigated later. Each of the companion design documents (Authentication, Authorization, Secrets Storage, Risk Exception Tracking, Interface Extensibility, Audit Logging, Application Structure, Data & Editing Behavior) has been updated to reflect the resolved decisions below — this register is the index of all of it in one place, plus everything that hasn't been designed yet at all.

Update this document as decisions get made, rather than letting resolutions live only in conversation history.

## Resolved Decisions

| ID | Area | Decision | Resolution |
|---|---|---|---|
| D-01 | Authentication | Should a break-glass path exist if all configured providers fail? | Approved — a break-glass path will be included. |
| D-02 | Authentication | Should the login screen remember the last-used provider? | Approved — the login screen will default to the user's last-used provider. |
| D-03 | Authorization | Can a user hold more than one role at once? | Yes — effective permissions are the union of every role a user's group memberships grant. |
| D-04 | Authorization | Do role/permission changes apply immediately, at next login, or something else? | Neither extreme — a "Reload Rights" action (self-service and admin-triggered) refreshes a session's permissions on demand. |
| D-05 | Authorization | Role model structure | Shifted from a fixed role hierarchy to a permission-based model: `app_permission` + `role_permission` (many-to-many), so a permission like `ApproveExceptions` can be granted through more than one role. |
| D-06 | Secrets Storage | Which secret store backends must be supported? | Modular support for six: Azure Key Vault, AWS Key Store, Windows DPAPI, CyberArk CCP, CyberArk CP, CyberArk Conjur. |
| D-07 | Risk Exceptions | Who can add/approve a risk exception? | Controlled by a permission (`ApproveExceptions`), assignable to one or more roles — not hardcoded to a single named role. |
| D-08 | Extensibility | Should ad hoc, non-migrated custom fields be supported? | No — every field stays governed through a proper schema migration, no exceptions. |
| D-09 | Infrastructure | Single server or a load-balanced farm for the dev environment? | Single server — SQL Server and IIS on the same box. This resolves the DPAPI-NG question: plain Windows DPAPI is viable without the AD-scoped DPAPI-NG variant, since there's no second node that needs to decrypt what another node encrypted. |
| D-10 | Audit | How deep does the audit trail need to go for in-app edits? | Full field-level diff log: who changed what, from what, to what, when — for every edit, not just a high-level action log. See `Design_Audit_Logging.md`. |

| D-12 | Audit | How is audit log retention controlled? | A global application configuration page lets an admin set the retention period — not a hardcoded value. See `Design_Audit_Logging.md`. |
| D-13 | Authorization | Does Reload Rights re-query the live IdP/AD, or refresh from a cached snapshot? | Live query — Reload Rights re-fetches current group membership from the IdP/AD in real time, not from a cached snapshot. |

| D-15 | Secrets Storage | Does "AWS Key Store" mean AWS Secrets Manager, AWS KMS, or both? | AWS Secrets Manager specifically. |

Which specific backend gets built first, and the exact per-backend request/response shape, is deferred (see Q-08 below). |
| D-17 | Risk Exceptions | Is ExceptionID a simple internal sequence, or does it need to align with an external scheme? | Neither fixed choice — the numbering scheme needs to be flexible/configurable, since it will differ by organization. |

This requires a new `dim_application`-style entity that doesn't exist in the schema today — the entity design itself is not yet resolved (see Q-25 below). |

| D-20 | Extensibility | Should `RequiredPermission` support per-field granularity from day one? | No — deferred for now. Ship with a single blanket "can edit this record" permission; per-field granularity can be added later if actually needed. |
| D-21 | App Structure | Front-end approach: server-rendered pages or a SPA framework? | JavaScript-based, either plain JS/fetch or a SPA framework — optimized to be light and fast. | D-22 | App Structure | Where's the line between this app and Power BI? | They coexist: the app gets its own dashboards/reports to support an analyst's day-to-day workflow, while Power BI continues to serve broader/aggregate reporting off the same data (`04_BlueTrack_PowerBI_Support.sql` stays relevant). |
| D-23 | Authentication | Which third-party library implements SAML 2.0 for ASP.NET Core? | ITfoxtec.Identity.Saml2. |
| D-24 | Authentication | Who holds the break-glass credential, and how is its use audited? | Stored securely in the CyberArk product itself, like any other privileged credential — not in this app's own secret store. Its use triggers an active alert, in addition to passive capture in the general audit log (D-10/D-11). Fully resolves former Q-01. See `Design_Authentication_Architecture.md`. |
| D-25 | Authentication | How is SAML IdP metadata/certificate trust handled? | Pulled once and embedded as local config, not fetched dynamically at runtime. Refresh (for cert rotation) is manually triggered, over TLS, with the fetched certificate's thumbprint checked against the expected value — fail closed on mismatch. See `Design_Authentication_Architecture.md`. |
| D-26 | Authentication | What SAML assertion validation is required? | Enforce `SubjectConfirmationMethod` = bearer; enforce `NotBefore`/`NotOnOrAfter` with a couple minutes of clock-skew tolerance; reject unsigned assertions/responses where signing is expected; log and alert on any rejected assertion. See `Design_Authentication_Architecture.md`. |
| D-27 | Authentication | Operational safeguard for the SAML trust relationship? | A manual or automated reminder ahead of the IdP's certificate expiration date, since an expired-cert outage is a more likely failure mode than an attack. See `Design_Authentication_Architecture.md`. |
| D-28 | Infrastructure | Session idle timeout policy? | Configurable, starting at 30 minutes. Resolves the timeout half of former Q-23. |
| D-29 | Infrastructure | Which actions need MFA step-up within an already-SSO'd session? | Only configuration settings and security settings — not general workflow actions like approving an exception. Resolves the step-up half of former Q-23. |
| D-30 | Infrastructure | How does the app connect to SQL Server? | Windows Integrated Authentication, using a dedicated low-privilege domain service account (or gMSA) as the app pool identity — not the default `ApplicationPoolIdentity` machine account, and not `db_owner`, just grants scoped to what the app needs. Chosen over a SQL login to avoid introducing a standing secret at all (fits D-06/Secrets Storage's spirit) and because it fits the confirmed single-server topology (D-09) with no Kerberos double-hop to solve. Caveat: if a future production topology splits SQL Server onto its own box or introduces a farm, this needs Kerberos delegation/SPN setup. Resolves former Q-21. |

Populated as a curated mapping, like `platform_account_type_map`, not inferred from Safe names. Fully resolves former Q-25. See `Design_Risk_Exception_Tracking.md`. |

See `Design_Secrets_Storage.md`. |

| D-58 | Infrastructure | How do schema changes get promoted into Test/Staging/Prod (D-54), given drop-and-recreate is destructive past Dev? | DbUp — a small .NET library that runs hand-written, numbered `.sql` scripts in order and tracks what's applied in a journal table. | D-62 | Audit | Where does the audit retention purge run, and is it itself recorded? | A SQL Agent job calling a stored procedure (e.g. `usp_PurgeAuditLog`) — matches the existing documented pattern for `usp_RunFullLoad` and the history-snapshot job, rather than introducing an app-level scheduler. | D-63 | Audit | Does the audit log need to be tamper-evident? | No cryptographic tamper-evidence for now — standard DB access control (insert-only app grants, delete only via the purge job's identity). | D-64 | Database | Should the web-interface tables designed this session live in a separate database from the existing CyberArk-mirroring/ETL tables, or stay together? | One database, but a separate `web` schema (not the default `dbo` everything else uses) for the tables designed this session: `identity_provider_config`, `app_permission`, `app_role`, `role_permission`, `identity_group_role_map`, `app_user`, `dim_application`, `dim_exception_status`, `risk_exception`, `account_progress_lock`, `dim_audit_event_type`, `audit_event`, `audit_field_change`, `audit_purge_log`, `audit_config`, `app_config`, and the field-metadata table (`Design_Interface_Extensibility.md`). A separate *database* was rejected — SQL Server has no cross-database FK enforcement, and several of these tables FK directly into `dbo` tables (`risk_exception.AccountKey` → `fact_account`, `dim_safe.ApplicationKey` → `dim_application`, `account_progress_lock.AccountKey` → `fact_account`, `fact_account_progress.ExceptionKey` → `risk_exception`) — splitting databases would mean losing referential integrity on all of them and needing distributed transactions (MSDTC) for actions that touch both sides atomically. | D-65 | Infrastructure | Does a SQL Server backup of `BlueTrack` capture everything BlueTrack needs? | No — several real gaps, most notably that Windows DPAPI-encrypted secrets (the first backend built, D-36) are bound to the originating machine and can't survive a restore to different hardware, a disaster-recovery risk D-09 never considered (it only evaluated DPAPI against farm vs. single server). Also out of database-backup scope entirely: the actual secret values behind any backend (Azure Key Vault/AWS Secrets Manager/CyberArk CP hold them externally), the break-glass credential (lives in CyberArk, D-24), and the SAML signing certificate/embedded IdP metadata (Windows Certificate Store and local deployment files, D-25/D-34).
