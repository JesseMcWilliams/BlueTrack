# BlueTrack: Audit Findings (open)

> **Stage: Testing.** Open findings from documentation, deployment and live-verification audits. Add new findings here; when one is resolved, move it to `Archive_Testing_Audit-Findings.md`.

## Deployment

- [ ] **Found 2026-09-24, while verifying D-162/D-163 end to end with a real SQL grant (D-164)**: `Database/41_BlueTrack_GrantAppServiceAccountAccess.sql` correctly grants the app's own database permissions, but the real host still fails every DB-touching request with `Login failed for user 'DOMAIN\HOSTNAME$'. Reason: Could not find a login matching the name provided` -- not a permissions error, and not fixed by the login existing, being enabled, having the correct SID (confirmed three independent ways), or toggling the App Pool's `loadUserProfile`. Matches a known, general limitation of `ApplicationPoolIdentity` for outbound Windows-authenticated connections to remote services like SQL Server. **Not fixed** -- needs a real environment decision (switch the App Pool to a dedicated domain service account or gMSA), not something to guess at further; see D-164 and `User_Docs/Admin_OperationsGuide.md`'s "Granting the app's own SQL Server access" section.

## Security review 2026-10-10 (open)

Five-area review (auth/session, SQL/data access, uploads/feeds/secrets, frontend/HTTP, deployment/CI). Fixed items are in `Archive_Testing_Audit-Findings.md` under the same date (D-197).

- [ ] **Medium (was High) -- CI runs pull-request code on the self-hosted runner (this host).** `.github/workflows/ci.yml` triggers on `pull_request` with `runs-on: [self-hosted, ...]` and the repo is public. **Mitigated 2026-10-10:** the repository now requires approval before any outside contributor's workflow runs, and `ci.yml` has `permissions: contents: read` and `actions/checkout` pinned to a commit. **Remaining:** approving a pull request still runs its code here, so review a PR's changes (especially to `ci.yml`, `package.json`, tests and scripts) before approving its run; making the repository private, which GitHub recommends for self-hosted runners, was declined for now.
- [ ] **Info -- admin-only troubleshooting endpoints return exception text** (backup, credential test, SMTP test, feed test): kept on purpose (D-197), since that text is how an admin diagnoses the failure.
- [ ] **Medium -- backup files readable by every local user (checked 2026-10-12).** `BlueTrack.Rollback.psm1` creates the backup folder with inherited permissions. On the dev host, `C:\Data\Backups` inherits from `C:\`, so `BUILTIN\Users` can read `BlueTrack_*.bak`: a full copy of the database, including Machine-scope DPAPI credentials that any local process can decrypt until first use (D-116). SQL Server's default `...\MSSQL\Backup` folder is not affected (no Users entry). **Fix needs a decision:** which accounts get access (Administrators, SYSTEM, the SQL Server service account to write, the App Pool account to delete old scheduled backups, D-200), as D-197 did for the update download folder.
- [ ] **Blocked -- LDAPS from the dev host to itself fails (checked 2026-10-12, twice).** This host is a DC with LDAPS on 636 and a trusted self-signed certificate (`CN=WIN-K5POLANERI5.Company.com`, in `LocalMachine\Root`, chain valid; a .NET TLS 1.2 handshake works). Remote LDAPS works: Authentik's LDAP source syncs from this DC over `ldaps://` (last success 2026-10-13 04:47 UTC). But every Windows LDAP client bind over 636 *from this host* fails: first they hung for 3+ minutes, on the retry they fail after about 37 s with "server could not be contacted" / "LDAP server is unavailable" (`PrincipalContext` with `SecureSocketLayer | Negotiate`, as `LdapContextFactory` does with `UseSsl`; `System.DirectoryServices.Protocols`, Negotiate and anonymous). No Schannel or Directory Service events at default logging. So BlueTrack with `UseSsl` can't be proven on this host. Next: run the same bind from DCACYBSQL01, or turn on Schannel event logging here.
- [ ] **Medium -- secrets backends accept `http://` URLs.** `CyberArkCcpSecretsProvider.cs:56` and `CyberArkConjurSecretsProvider.cs:90,96` take any scheme, and nothing validates BackendSettings on save. An `http://` CCP URL returns the password in clear text; Conjur POSTs its decrypted API key in clear text (line 99). Fix: require an absolute `https` URI on save and in each provider.
- [ ] **Medium -- the CP/CCP fallback cache never expires and its key is too narrow.** `CyberArkCpSecretsProvider.cs:25,36`, `CyberArkCcpSecretsProvider.cs:29,35`: a static dictionary keyed on Safe|Folder|Object only, with no TTL or eviction. Every secret fetched (Test buttons included) stays in memory for the life of the process, and after a change of AppID or CCP host a transient error still returns the old configuration's secret. Fix: add AppId and BaseUrl to the key, cap the fallback age, clear the cache when the backend is saved.
- [ ] **Low -- a CCP timeout returns a 500 and skips the cache fallback.** `CyberArkCcpSecretsProvider.cs:69` catches only `HttpRequestException`; a timeout (`TaskCanceledException`) or bad JSON (line 94) is unhandled, and the response isn't disposed.
- [ ] **Low -- the secrets HttpClients follow redirects.** `Program.cs:106,128` use the default handler. A 307/308 from Conjur re-sends the POST body (the API key) to the new host. Fix: `AllowAutoRedirect = false` and an explicit timeout on both clients.
- [ ] **Low -- the Azure, AWS and Conjur bootstrap credentials stay Machine-scope DPAPI.** `WindowsDpapiProtector.cs:28` (constant entropy); unlike D-116's credentials they're never upgraded to User scope, so any local process that can read `web.secrets_store` (or a backup, see above) can decrypt them.
- [ ] **Low -- Azure and AWS secret calls can block for minutes** (SDK default retries and timeouts, a new client per call), and a bad `VaultUri` throws outside the try at `AzureKeyVaultSecretsProvider.cs:74`.
- [ ] **Info -- the Conjur access token may be sent in the wrong format.** Line 110 uses the raw authenticate response; Conjur's docs call for it base64-encoded (or `Accept-Encoding: base64`). Not confirmed; check before the first live Conjur test.
- [ ] **Low -- an unreadable SAML SP signing key gives an unhandled 500 at `/api/auth/saml/login`** ("Keyset does not exist"). Found 2026-10-12: the dev site's SP thumbprint pointed at the IIS TLS certificate, whose key the App Pool account can't read. The dev host now uses a dedicated SP certificate. The app should report this clearly (as the health check could), and the installer docs should say the SP certificate needs a key readable by the App Pool account.
- [ ] **Low -- the secrets-store and credential Test buttons aren't audit-logged.** `SecretsStoreController.TestConnection` takes any Safe/Folder/Object and returns its UserName, Address and password length; `CredentialsController.Test` likewise. A `ManageSecretsStore` holder can probe vault objects with no audit trail (CP/CCP AppId rights are the only limit). Fix: audit each test call with what was asked and the outcome; consider dropping the password length.
