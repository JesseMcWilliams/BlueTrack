# Web Interface Design Document — Deployment Methodology

**Blueprint Progress Tracking Web Interface**

## Purpose & Scope

No deployment doc existed anywhere in this project before now — confirmed by a direct file search during the 2026-09-05 documentation/deployment audit. Everything that touches "how does a build actually get onto a real server" had to be pieced together from what already exists (`App/Migrator`, `.github/workflows/ci.yml`, `appsettings.json`, D-09's single-server assumption) rather than read from one place. This document is that one place, going forward.

**Scope boundary, matching `Design_Testing-Strategy.md`'s own stance**: CI (`ci.yml`) is explicitly a test-verification pipeline only — it stops after Playwright's E2E run, never builds a release artifact, never touches the real `BlueTrack` database, never interacts with IIS. Everything from "build a release artifact" onward is this document's territory, not CI's.

## Environment & Hosting

Per D-09: single server, SQL Server and IIS on the same box, for every environment (Dev/Test/Staging/Prod, D-54's naming). No web farm, no load balancer — this materially simplifies deployment (no need to coordinate a rolling update across multiple nodes) but also means there's no redundancy to fail over to during a deploy; a deploy is a real, brief interruption of the one running instance.

**D-108: IIS hosting is static for the SPA.**
- **`App/Web/dist/`** (the built Vue SPA), copied to its own install folder (`WebInstallPath`, D-187), is served as static files at the IIS site's physical root. No Node/Vite process runs in a real deployment.
- **`App/Api`** is a nested IIS Application at `/BlueTrack`, hosted in-process by the ASP.NET Core Module (ANCM).
- The production SPA calls the API at `/BlueTrack/api/...` (`VITE_API_BASE` in `App/Web/.env.production`, applied by `App/Web/src/utils/apiBase.js`, D-196). In development the Vite proxy serves it at `/api/...`.
- The site-root `web.config` is written by the `Iis.WebConfig` step from `Deploy/Templates/site-web.config.template` (`Set-BlueTrackSiteWebConfig`, `Deploy/Modules/BlueTrack.Iis.psm1`): a URL Rewrite rule answers `/api/...` with a 404 (D-196), and an SPA fallback rule serves `index.html` for paths that aren't real files.

## Deployment Steps

`Install-BlueTrack.ps1` runs these as named steps (next section); single-server and no redundancy, so it stays a small, explicit sequence.

1. **Backup (`Db.Backup`).** Before migrating a database that already has a schema, takes a verified, manifested backup via `Deploy/Modules/BlueTrack.Rollback.psm1` (Open Questions, rollback). `msdb` (SQL Agent jobs, D-66) is backed up only with `Backup-BlueTrack.ps1 -IncludeMsdb`.
2. **Build (`Build.Api`, `Build.Web`).** `dotnet publish -c Release` for the API and `npm ci` + `npm run build` for the SPA (`Deploy/Modules/BlueTrack.Build.psm1`), output straight to the install paths. No `.pubxml` is used.
3. **Migrate (`Db.Migrate`).** `App/Migrator` against the target database. It runs only the top level of `Database/`; the SQL Agent job and grant scripts in `Database/Manual/` are run by hand or by the `Db.NightlyJob`/`Db.AppPoolAccess` steps. Safe to re-run: DbUp's journal skips what has already run. On a database built from the pre-baseline scripts it records the baseline as applied instead of running it (D-195, below).
4. **Site settings (`Db.AppSettings`, D-230).** Writes `appsettings.Site.json` next to the published API: the connection string, `Security:EnableHsts`, `FileAccess:AllowedRoots`, and `BlueTrack:EnvironmentName` (the Environment answer, which the Deployment page shows). With SQL authentication the file is limited to Administrators, SYSTEM and IIS_IUSRS (D-197). It then removes the `appsettings.<Environment>.json` earlier installers wrote; an old `appsettings.Production.json` that holds other settings is kept, with a warning, because ASP.NET Core still loads it.
   - **Why a site file, and why the API stays Production.** IIS runs the API as ASP.NET Core **Production**: nothing sets `ASPNETCORE_ENVIRONMENT`, and setting it to `Development` would turn on the dev-only test sign-in, DevFakeAuth, OpenAPI and `BlueTrack:DisableNegotiate`. So an `appsettings.Test.json` (or Staging, Development) was never loaded. `Program.cs` loads `appsettings.Site.json` in every environment except Development, right after `appsettings.{env}.json`: it overrides `appsettings.json`, and environment variables and command-line arguments still override it. Development (`dotnet run`, the tests, E2E) never loads it, so a stray copy can't point them at a site's database.
   - **Survives `Build.Api`.** `dotnet publish -o` doesn't clean the output folder, and the API project excludes `appsettings.Site.json` from build and publish output (and `.gitignore` excludes it), so a publish never overwrites it. The API reads it at startup only: `Iis.WebConfig` (which recycles the app pool) applies a change.
5. **IIS (`Iis.AppPool`, `Iis.Certificate`, `Iis.Site`, `Iis.WebConfig`, `Iis.SiteRestart`).** Creates the app pool, HTTPS binding, site and nested `/BlueTrack` Application, writes the site-root `web.config`, recycles the app pool and restarts the site.
6. **Smoke test (`Smoke`).** `Deploy/Modules/BlueTrack.Smoke.psm1` calls `/BlueTrack/api/admin/deployment` (the Deployment Info admin page's data, `Design_Admin-Deployment-Management.md` Part 3), prints each health check, and checks that the site root serves the SPA's `index.html`.
7. **Manual operator checks.** After a first install, confirm the Identity Providers, Secrets Store and (D-106) DPAPI `ProtectionScope` admin settings are right for this environment. If an OIDC setting (enable, Authority, ClientId, secret) is saved outside a deploy, recycle the app pool: OIDC schemes are registered at startup (`Design_Authentication-Architecture.md`); a deploy's recycle already covers it.

### Installer steps, resume and prerequisite sources (D-168)

`Install-BlueTrack.ps1` runs the sequence above as named steps (`Prereq.*`, `Build.*`, `Db.*`, `Iis.*`, `Smoke`). Answers and each step's outcome are saved under `Deploy/State/`, so a failed install continues with `-Resume`, and any step can be re-run with `-Step` or `-StartAt`. Prerequisites install from an offline installer folder, winget, or the vendor's release metadata, in that order under `-PrerequisiteSource Auto`, and every installer is hash- and signature-checked before it runs. Usage: `Deploy/README.md`. `Update-BlueTrack.ps1` (D-192) fetches a release, `main` or a chosen branch as GitHub's source zip into a per-version folder under the saved `UpdateDownloadFolder`, copies the site's saved answers into it, and offers to run that copy's installer.

### IIS restart, the browser path, and redeploying over a running API (D-172, D-175)

After IIS changes and an app pool recycle, browser sign-in through the rewritten `/api/...` path can loop (`401.1`) while `/BlueTrack/...` works; on DCACYBSQL01 only a full `iisreset` cleared it. So the optional `Iis.Reset` step (`-ResetIis`) restarts IIS after the IIS steps, and the smoke test now also calls `/api/admin/deployment` through the site root, the browser's path. D-172's Windows auth at the site root is kept, but it was not the fix it appeared to be. `Build.Api` uses `app_offline.htm` to release a running API's files before publishing over them. D-188: on the dev host `iisreset` did not clear the loop but a site configuration change did, so `Iis.SiteRestart` now always stops and starts the BlueTrack site after the IIS steps (re-registering its URLs and sign-in settings with HTTP.sys, which `iisreset` leaves running).

**D-196 (2026-10-10) removed the rewritten path.** The loop came back on DCACYBSQL01 after a deploy that ran `Iis.SiteRestart`, with identical Windows auth settings at the root and `/BlueTrack`; turning kernel-mode auth off broke both paths. So the SPA's production build now calls `/BlueTrack/api/...` directly (`VITE_API_BASE` in `App/Web/.env.production`, applied by `App/Web/src/utils/apiBase.js`), the path that always signed in, and the site-root `web.config` answers `/api/...` with a 404 instead of rewriting it. The smoke test calls `/BlueTrack/api/admin/deployment` (the SPA's own path) and checks that the site root serves the SPA. `Iis.SiteRestart` and the optional `Iis.Reset` stay, as harmless. Confirmed fixed on DCACYBSQL01 (2026-10-10).

### The schema baseline and drift check (D-195)

Before the first release, the numbered scripts `01`-`51` were consolidated into six baseline scripts (`Database/01`-`06_BlueTrack_Baseline_*.sql`) that build the same schema and seed data from an empty database; `Deploy/Compare-BlueTrackSchema.ps1 -IncludeData` found no difference between a database built each way. DbUp records scripts by name only, so `App/Migrator` checks the journal first: a database whose journal shows the old scripts through `51_BlueTrack_TargetsFromCyberArkAddress.sql` gets the six baseline names recorded as applied without running them (running them would wipe its data); one built from the old scripts but not up to `51` is refused, to be upgraded from the `pre-sql-baseline` tag first. Existing deployments therefore upgrade with the normal installer or `Update-BlueTrack.ps1`, with no data copy. Afterwards, the drift check (`Database/README.md`, "Drift check") compares the live database with a reference built from the scripts; on the dev host the only difference was one view's comment, which `-IgnoreComments` hides. New schema changes are small, guarded scripts numbered from `07`.

### App pool SQL access and smoke-test diagnosis (D-170, D-171)

With Windows Integrated Security, the `Db.AppPoolAccess` step (opt-in via `-GrantAppPoolSqlAccess`) gives the App Pool's Windows account a SQL login and the grants in `Database/Manual/02_BlueTrack_GrantAppServiceAccountAccess.sql`. For `ApplicationPoolIdentity` that's `IIS APPPOOL\<pool>` when SQL Server is on the same machine (the D-09 layout) and the computer account `DOMAIN\HOSTNAME$` when it's elsewhere; a custom identity is itself. A failed smoke test is explained by HTTP status (401: IIS rejected the Windows login, try `klist purge` then `-Step Smoke`; 403: the account lacks `ViewDeploymentInfo`; 500 or above: an app error, plus SQL Server's recent `Login failed` event with the account from the event's SID, since the message text can name the wrong one; no response: DNS, binding or certificate), and ends by listing the two URLs to try by hand: the API at `/BlueTrack/api/admin/deployment` and the site root. Details: `Deploy/README.md`, "App pool SQL access" and "Smoke test failures".

### The nightly job and CyberArk source settings (D-176, D-211)

The `Db.NightlyJob` step (opt-in via `-InstallNightlyJob`) runs a temporary copy of `Database/Manual/04_BlueTrack_ScheduleImportLoadJob.sql` with its four tokens filled from `-ImportSources`, `-ExportFolderPath` and `-EvdDatabaseName`. The job itself holds no source settings: its Import (since D-224 the job's one step is `EXEC usp_RunNightlyImportLoad;`, which runs the Import, the Load and then the daily snapshot even when either failed) is `EXEC usp_Import_Configured;`, which reads `web.cyberark_source_config` (edited on Admin > Data Sources). The script writes that row only when none exists, so the installer's answers seed the settings on first install and the page owns them afterwards; when a row exists and differs, the script keeps it and prints a WARNING. An install from before D-211 keeps its old job, with the values written into it, until `-Step Db.NightlyJob` is re-run; likewise an install from before D-224 keeps its two-step job (no snapshot on a night the Import fails) until then. Details: `Deploy/README.md`, "A note on the nightly Import+Load job".

### The Site URL (D-224)

`Db.SiteUrl` (after `Db.AppSettings`, needs `Database` and `Hostname`) sets `web.app_config.SiteUrl` to `https://<Hostname>[:<HttpsPort>]` (no port when 443) only when it is empty, through a parameterized `UPDATE ... WHERE SiteUrl IS NULL OR blank`, so an admin's value on Global Application Configuration always wins. `Get-BlueTrackSiteUrl`/`Set-BlueTrackSiteUrl` live in `BlueTrack.Database.psm1`; under `-WhatIf` the step doesn't connect. Details: `Deploy/README.md`, "The Site URL".

### Releases and the version stamp (D-226)

A release is made with `Tools/New-BlueTrackRelease.ps1` in two runs, because `main` changes only by pull request. `-Version x.y.z [-Date] [-Push]` checks the clone (on `main`, clean, equal to `origin/main`, version above the latest `v*` tag, no existing tag or branch, Unreleased not empty, python-docx importable), then on branch `YYYY-MM-DD-release-vX.Y.Z` sets `<Version>`, renames Unreleased to `## X.Y.Z (date)`, rebuilds `Published_Docs/` and adds a new empty Unreleased, commits, and with `-Push` opens the PR. After the merge, `-Tag [-Push]` signs `vX.Y.Z` (D-199) on the `origin/main` commit that set `<Version>`, pushes it, creates the GitHub release from that version's notes and checks GitHub verified the signature. Usage: `Tools/README.md`, "Making a release".

Between releases the `BlueTrackStampVersion` target in `BlueTrack.Api.csproj` sets InformationalVersion from `git describe --tags --long --match "v[0-9]*"`: `X.Y.Z` on the release tag, `<Version>-dev.<commits>+<sha>` after it, `<Version>-dev+<sha>` without a reachable tag (CI's shallow checkout), `.dirty` for tracked changes. Without git or `.git`, as in the source zip `Update-BlueTrack.ps1` installs from, it's plain `<Version>`, which a release sets, so a release install shows its version. A build never fails because of git: each call ignores its exit code. About and the Deployment page show this string.

## Open Questions

- ~~No rollback mechanism exists anywhere~~ — **Resolved 2026-09-16 (Option B from `Archive_Planning_Outstanding-Work-Survey-2026-09-16.md`)**: full-database backup/restore is the formal rollback mechanism, not per-script down-migrations. `Deploy/Backup-BlueTrack.ps1`/`Restore-BlueTrack.ps1` (backed by `Deploy/Modules/BlueTrack.Rollback.psm1`) take a verified, manifested backup and can restore from a specific one; `Install-BlueTrack.ps1` now runs the backup automatically before migrating an existing (non-fresh) database, resolving step 1 above rather than leaving it a manual checklist item. `msdb` (needed for SQL Agent job definitions, per D-66) is included only when explicitly requested (`-IncludeMsdb`/`-RestoreMsdbFilePath`), since restoring it is instance-wide, not scoped to just BlueTrack. **D-203 (2026-10-12):** backups hold credentials, so the backup folder is limited to specific accounts by `Set-BlueTrackBackupFolderAccess` (called by `Backup-BlueTrackForRollback`), and the API enforces the same before each backup it takes (`BackupFolderAccess`: fix it if allowed, else refuse). **What this does not solve**: there are still no down-scripts for the numbered `Database/*.sql` files — full-database restore remains the only rollback path, which is what Option B always meant; per-script down-migrations for the highest-risk schema changes remain a possible future investment, not something this pass attempted.
- ~~No environment-specific `appsettings.*.json` pattern exists~~ — **Resolved 2026-09-11, replaced by D-230 (2026-10-14)**: the installer writes `appsettings.Site.json`, which the API always loads (step 4). The 2026-09-11 `appsettings.{Environment}.json` was never loaded, because IIS runs the API as Production.
- ~~The `.pubxml` publish profile and IIS `web.config`/site structure don't exist yet~~ — **Resolved 2026-09-11**: `Deploy/Install-BlueTrack.ps1` runs `dotnet publish` directly (no `.pubxml` needed for that), and creates the IIS site/Application Pool/nested `/BlueTrack` Application plus the site-root `web.config` (SPA fallback URL Rewrite rule) itself — see `Deploy/README.md`. **Verified end to end on a real new server (2026-10-07)**: DCACYBSQL01 ran every step and passed the smoke test, after the D-168 to D-171 fixes that run surfaced (the last SQL grant applied by hand, before `Db.AppPoolAccess` was corrected in D-171). Still untested: SQL Server on a different machine from IIS.
